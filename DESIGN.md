# HowMacro Design (console / plain .NET stage)

## In one sentence

Macros are **real C# code**: a method macro is a method marked `[Macro]`, an attribute macro is an attribute class marked `[AttributeMacro]`, and a region macro is a method marked `[RegionMacro]`.
The IDE treats `@GETSET(...)` and `[@Save]` as ordinary method calls and attributes (completion, type checking, F12 into the macro's implementation);
before compilation, the expander **runs the macro's method body (or constructor body)** to get the code; at runtime only the expanded code remains.

```csharp
// macro library Demo.Macros
[Macro(MacroSite.Member)]
public static T GETSET<T>(T target)
{
    var path = Macro.Arg(0);
    Macro.Emit($"{Macro.Modifiers} {Macro.Type} {Macro.Name} {{ get => {path}; set => {path} = value; }}");
    return default!;
}

// application code
public int Hp = @GETSET(DataCenter.PlayerData.Hp);
// what the compiler actually gets:
public int Hp { get => DataCenter.PlayerData.Hp; set => DataCenter.PlayerData.Hp = value; }
```

## Core principle: the unexpanded project must stay statically correct

**Names and types are declared only in source; macros change only the implementation.**

Macros solve boilerplate that design patterns can't remove, such as "every Player property must log when it changes".
Wrap it in a macro once instead of writing almost the same code in every setter:

```csharp
public int Gold = @LOGGED(100);
public int Level = @LOGGED(1);
public string Title = @LOGGED("Novice");
```

The IDE sees three fields; the compiler gets three logging properties. For all code that uses `Gold` they are equivalent,
so the IDE's completion, navigation, rename and type checking can always be trusted — **no IDE plugin or source generator needed**.

The engine enforces this principle:

| Scenario | Rule | On violation |
|---|---|---|
| Member method macro | The expansion must be exactly one field or property whose name and type match the source declaration, plus optionally private fields for the macro's own state (see below) | HMC008 (name) / HMC009 (type) |
| Statement method macro | The expansion is wrapped in `{ }` automatically; locals declared by the macro can't escape the block | Can't happen |
| Expression method macro | Never introduces names | Can't happen |
| Attribute macro | Doesn't change the declaration it marks; its fragments may only reference names that exist in source | HMC013 when it references a missing name |
| Region macro | Per-member replacement: same as Member method macros; whole-text replacement: field and property names and types unchanged, set of member names unchanged | HMC008 / HMC009 |
| Every macro call site | Must be valid C# before expansion: code that is only valid after expansion (permanently red in the IDE) is not allowed | HMC020 |
| Private state of a macro | Source code may not name a private field a macro added (it doesn't exist before expansion) | HMC021 |

The IDE can't see names generated by a macro, so by this principle such macros are disallowed outright rather than patched up afterwards.

**Private state of a macro**: a macro sometimes needs storage of its own, e.g. a property that logs each change needs a field
to keep the value in, and C# 9 (Unity) has no `field` keyword. So besides the declared member, a Member macro (or a region
macro's per-member replacement) may emit **private fields**. They are invisible outside the type, and the source can't name
them because they don't exist before expansion (if it tries, HMC021). Convention: name them `@_temp_<member>`, adding
`_2`, `_3`, ... when a member needs more than one; member names are unique within a type, so these never clash. A macro may
also take the name from its caller instead.

```csharp
// public int Gold = @TRACKED(5);  expands to
private int @_temp_Gold = 5; public int Gold { get => @_temp_Gold; set { @_temp_Gold = value; /* ... */ } }
```

**Checking the call site itself (HMC020)**: the rules above constrain macro output, but the way a macro is called can also violate the principle.
For example `public int Hp = @CLAMP(0, MaxHp, 20);`: before expansion this is a field initializer, which can't reference the instance member `MaxHp` (CS0236),
so the IDE keeps showing an error; after expansion `MaxHp` moves into the setter and it compiles. Before expanding, the engine checks every macro call site
(attribute macros included) for compile errors in the original source, and reports HMC020 for this kind of "only valid after expansion" code.

```
error HMC020: CS0236: A field initializer cannot reference the non-static field, method, or property 'Player.MaxHp' -- this code is only valid after @CLAMP is expanded, so the IDE shows it as an error. The unexpanded source must stay statically correct; rewrite the call so it is valid C# on its own
```

The fix is to make the call itself valid C#. For example, write a separate macro that names the upper-bound member with `nameof`: `@CLAMP_TO(0, nameof(MaxHp), 20)`.
`nameof(instanceMember)` is allowed in a field initializer and follows renames; the macro then uses semantic information to check that the member exists and has a matching type.
"Name / type / member not found" errors are not reported here: the compiler reports them after expansion anyway, and reporting them here
would produce false positives in projects that depend on types produced by source generators.

**Checking uses after a field becomes a property (HMC017)**: Member macros and region macros turn a field into a property with the same name and type.
For almost all code the two are equivalent, but a few uses only work on fields. The IDE sees a field and reports nothing; the build fails only after expansion,
with a compiler error that doesn't match the source. The engine finds these uses across the whole project and reports them on the line of the use:

- `ref` / `out` arguments, e.g. `Interlocked.Increment(ref p.Gold)`, `int.TryParse(s, out Hp)`
- `ref` expressions, e.g. `ref int hp = ref Hp;`
- Taking the address: `&p.Gold`
- Mutating the inside of a struct-typed member, e.g. `p.Pos.X = 1`, `p.Pos.X++`: a property returns a copy, so the change is lost

```
error HMC017: Gold is turned into a property by @LOGGED, so it can't be passed as `ref`. The IDE still sees a field here, but the compiled code has a property
```

## Three kinds of macros

| | Method macro `@X(...)` | Attribute macro `[@X]` | Region macro `#region @X` |
|---|---|---|---|
| Definition | Static method marked `[Macro(MacroSite...)]` | Attribute class marked `[AttributeMacro(MacroTarget...)]` | Static method marked `[RegionMacro]` |
| Expansion logic | Method body | Constructor body | Method body |
| Purpose | **Expands in place**, replacing the call | **Produces helper code fragments**, without changing the declaration it marks | **Processes a group of members inside a region** |
| Output API | `Macro.Emit(code)` | `Macro.Fragment` / `Macro.Startup` | `member.Replace(code)` per member, or `Macro.Emit(fullText)` |
| After expansion | The call is replaced | The attribute is removed from source | Members are replaced; `#region` becomes `#region [expanded] @X` |
| IDE support | Completion, navigation, type checking | Completion, navigation | None (text after `#region` is just a comment to the IDE) |
| Example | `@GETSET`, `@LOGGED`, `@LOG` | `[@Save]`: the field is registered with the save container automatically | `@LOG_ALL`: add automatic logging to a group of fields |

`[@Save]` is itself valid C#: the `@` makes the compiler look only for an attribute class named `Save`, without appending the `Attribute` suffix.

### Where attribute macro fragments go

**A. Consumed by a method macro**: an attribute macro emits fragments to a channel with `Macro.Fragment("track")`,
and a method macro reads them with `Macro.Fragments("track")` and stitches them into code. Each fragment carries information about the marked declaration (containing type, name, type, location).

```csharp
[@Track] public int Hp = @GETSET(...);
[@Track] public int Gold = @LOGGED(100);

Console.WriteLine(@DUMP_TRACKED(p));   // → ("Hp=" + p.Hp + ", " + "Gold=" + p.Gold)
```

**B. A generated startup script**: an attribute macro emits startup code with `Macro.Startup(code)`.
The engine collects all startup code into `HowMacro.Startup.g.cs`, which runs automatically when the program starts — no hand-written code needed:

```csharp
[@Save] public int Gold = @LOGGED(100);
[@Save("lv")] public int Level = @LOGGED(1);

// generated by the engine (each statement is mapped back to its [@Save] with #line):
[ModuleInitializer] internal static void Run()
{
    { SaveContainer.Register<Player>("Gold", o => o.Gold, (o, v) => o.Gold = (int)v!); }
    { SaveContainer.Register<Player>("lv", o => o.Level, (o, v) => o.Level = (int)v!); }
}
```

The attribute on the entry point is configurable with `HowMacroStartupAttribute`. Plain .NET uses `ModuleInitializer` by default;
Unity can later switch to `RuntimeInitializeOnLoadMethod`.

## Region macros

Wrap a group of members in `#region @NAME` … `#endregion` and let one region macro process them together.
Typical use: while testing, you want automatic logging on all of Player's fields — wrap them, and delete the two lines afterwards to restore the original.

```csharp
public class Enemy
{
    #region @LOG_ALL
    public int Hp = 50;
    public string State = "Idle";
    public readonly int Id = 1;                         // readonly: skipped by the macro
    public int Shield = @GETSET(DataCenter.PlayerData.Mp); // already expanded by @GETSET: skipped by the macro
    #endregion
}
```

### Two processing modes (pick one)

**Per-member replacement**: `Macro.RegionMembers` lists every member in the region, with name, type, modifiers, regular attributes, initializer text, semantic information,
`ExpandedBy` (whether another macro already expands it) and `CanReplace`. Call `member.Replace(code)` to replace it; members you don't replace stay as they are.
Each replacement stays on the member's original line and is checked individually by the Member method macro rules (a field or property with the same name and type).

```csharp
[RegionMacro]
public static void LOG_ALL()
{
    foreach (var m in Macro.RegionMembers)
    {
        if (!m.IsField || !m.CanReplace || m.Declaration?.CanWrite != true) continue;
        m.Replace($"{m.Attributes} {m.Modifiers} {m.Type} {m.Name} {{ get; set {{ ...log...; field = value; }} }} = {m.Initializer};");
    }
}
```

**Whole-text replacement**: `Macro.RegionText` is the original text between `#region` and `#endregion`; emit the replaced text with `Macro.Emit`.
Good for plain-text processing such as regex replacement. The output is used as-is (not folded onto one line), so:

- The output **may not have more lines** than the original, or the following line numbers would shift (HMC007); fewer lines are padded automatically.
- The result is checked as a whole: field and property names and types unchanged, set of member names unchanged (HMC008 / HMC009).
- The region may not contain other macros, because whole-text replacement would replace them too (HMC012).

```csharp
[RegionMacro]
public static void PUBLIC_ALL() => Macro.Emit(Regex.Replace(Macro.RegionText, @"\bprivate\b", "public"));
```

### Rules

- **Recognition**: text after `#region` that starts with `@` makes it a region macro; it may take constant arguments, e.g. `#region @NAME("x", 3)`.
  The engine looks up a static method marked `[RegionMacro]` by name in the referenced assemblies. If none is found or the name is ambiguous, it **reports an error and stops the build** (HMC015).
  Ordinary `#region`s are unaffected.
- **Scope**: only type bodies are supported for now; `#region` and `#endregion` must sit directly between members of the same class/struct.
  Placing them in a method body or at namespace level reports HMC003.
- **Order**: same phase as method macros, after all attribute macros, so region macros can also read fragments with `Macro.Fragments`.
- **Macros can't contain macros**: region macros can't be nested (HMC012); members that already contain a macro can't be replaced.
  For those, `CanReplace` is false; forcing a replacement reports an error that says which macro already expands the member.
- **One mode only**: using both per-member replacement and whole-text replacement reports HMC016.
- **IDE support**: text after `#region` is just a comment to the IDE, so region macros have no completion and no go-to-implementation. This is what sets them apart from the other two kinds.

## Semantic information

Macros don't just see text; they can query semantic information about types and members. The model is defined in Abstractions (`MacroType` / `MacroMember` /
`MacroParameter` / `MacroAttributeInfo`) and implemented by the engine with Roslyn, so **macro libraries don't depend on Roslyn**.

- **IDE view**: based on the source before expansion. Here `public int Gold = @LOGGED(100)` is an int field,
  and `ExpandedBy == "LOGGED"` records which macro will actually expand it. Macros and the IDE see the same facts, in line with the core principle.
- **Lazy**: only the parts you use are computed; what you don't use costs nothing.

| Entry point | What you get |
|---|---|
| `Macro.ArgSymbol(i)` | The symbol an argument refers to: `@GETSET(DataCenter.PlayerData.Hp)` → field Hp |
| `Macro.ArgTypeInfo(i)` | The type of an argument expression |
| `Macro.Declaration` | The declared or marked member (x in `x = @M()` for method macros; the field, property or method an attribute macro marks) |
| `Macro.TypeInfo` | The type of the declared member |
| `Macro.ContainingTypeInfo` | The containing type (the type itself when an attribute macro marks a type) |
| `Macro.FindType(name)` | Look up any type by metadata name |
| `MacroFragment.Declaration` | Semantic information for the member behind a fragment |

What you can query:

- **Types**: `Name` / `FullName` / `CodeName` (the `global::...` form for generated code), `Kind`, `IsValueType`, `IsNullable`,
  `TypeArguments`, `ElementType`, `BaseType`, `Interfaces`, `Members`, `Attributes`, `EnumValues`,
  plus helpers `Is(fullName)`, `Member(name)`, `Fields` / `Properties` / `Methods`, `HasAttribute(name)`.
- **Members**: `Kind`, `Type` / `TypeInfo`, `Accessibility`, `IsStatic`, `IsConst`, `IsReadOnly`, `IsInitOnly`,
  `CanRead` / `CanWrite`, `Parameters` (with default values and ref kinds), `ConstantValue`, `Attributes` (with arguments, and which ones are attribute macros),
  `ExpandedBy`, source location.

Example (see `samples/Demo.Macros/M.cs`):

```csharp
// GETSET checks its target before expanding:
var symbol = Macro.ArgSymbol(0);
if (!symbol.CanWrite) Macro.Error($"`{path}` is read-only, so {Macro.Name}'s setter can't forward to it");
// → Player.cs(32,20): error HMC100: @GETSET: `h.RO` is read-only, so A's setter can't forward to it

// DUMP walks the type's members and generates concatenation code at compile time — no reflection at runtime:
@DUMP(p)   // → "Player { Hp=70, Mp=7, Gold=150, Level=2, Title=Hero }"
```

## Expansion rules

1. **Attribute macros first, then method and region macros**. All attribute macros run in file and line order before any method or region macro,
   so the fragments those read are always complete.
2. **Macros can't contain macros**: a method macro's arguments can't contain macros, and neither can macro output; otherwise HMC012.
   To combine macros, expand into a local first: `var sq = @SQUARE(4); @LOG(sq);`. Every macro expands exactly once, so behavior is predictable.
3. **Several macros may share a line**, each expanding on its own: `[@Track, @Save] public int Gold = @LOGGED(100);`.
   Conflicts between macros are undefined behavior the macro author didn't cover; that's up to the macro author.
4. **An error during expansion stops the build**. All macros still run, so every error is reported in one go instead of stopping at the first.
5. **Compile errors after expansion are reported too**. After a successful expansion the engine compiles the lines macros generated and the startup script.
   On failure it reports HMC013 and names the macro that generated the code, e.g.
   `Player.cs(6,21): error HMC013: code generated by @BAD_GEN doesn't compile: CS0103 ...`.
   Errors in application code itself are not checked here; the compiler reports them as usual. Turn this step off with `HowMacroVerify=false`.

## Packaging and installation

### NuGet packages

| Package | Referenced by | Contents |
|---|---|---|
| `HowMacro` | Projects that write macros and projects that use them | `ref/netstandard2.0/HowMacro.Abstractions.dll`: the API for writing macros, **compile-time reference only**, never a runtime dependency of the program<br>`build/HowMacro.targets`: auto-imported by NuGet, expands macros before compilation<br>`tools/net10.0/`: the prebuilt expansion tool and its dependencies (Roslyn) |
| `HowMacro.Testing` | Test projects for macros | Test helpers, engine, API; depends on `Microsoft.CodeAnalysis.CSharp` |

Build them with `dotnet pack pack/HowMacro -c Release` and `dotnet pack src/HowMacro.Testing -c Release`; packages go to `artifacts/packages/`.
The version lives in `HowMacroVersion` in `Directory.Build.props`.

`HowMacro.targets` decides how to run on its own:

- **Package mode**: inside the package, `tools/` contains the prebuilt expansion tool, which is used directly.
- **Source mode**: inside this repository, the expansion tool is built from source, so the samples in the repo can reference source directly without packing first.

### Two ways to write macros

**In-project macros**: good for getting started and small projects.

```xml
<PackageReference Include="HowMacro" Version="0.1.6-preview" PrivateAssets="all" />
<HowMacroDefinition Include="Macros/**/*.cs" />
```

- In the IDE, files under `Macros/` compile like ordinary source, so macros keep completion, navigation and type checking.
- In a real build, the expansion tool first compiles them separately into a temporary assembly (`obj/.../howmacro/<project>.HowMacroLocal.dll`),
  loads the macros from it to expand the project, then removes those files from the real compilation.
- Constraint: macro files compile before the project, so they can only use the HowMacro API and the project's referenced libraries, not the project's own types (HMC018).
  Conversely, application code can't use ordinary types from macro files, because macro files exist only at compile time (HMC019).
  HMC019 relies on the runtime cleanup analysis; when that analysis is unreliable (e.g. the project depends on types produced by source generators), the check is skipped.

**A separate macro library**: good when you have many macros or share them across projects.

```xml
<!-- MyMacros.csproj -->
<TargetFramework>netstandard2.0</TargetFramework>
<LangVersion>latest</LangVersion>
<PackageReference Include="HowMacro" Version="0.1.6-preview" PrivateAssets="all" />

<!-- the project that uses the macros -->
<PackageReference Include="HowMacro" Version="0.1.6-preview" PrivateAssets="all" />
<ProjectReference Include="../MyMacros/MyMacros.csproj" />
```

Runtime cleanup recognizes the macro library too, so it never shows up in the program's output.

Both approaches were verified from scratch in brand-new projects outside the repository, using a local package source.

## Runtime cleanup

Macro libraries are only useful at compile time; after expansion the program shouldn't depend on them. On every build the engine:

1. **Removes unused usings that import macro libraries**, e.g. `using static Demo.Macros.M;`. Only that line is blanked, so line numbers don't change.
   Otherwise the compiler would keep references to macro library types in the assembly for the PDB's import information.
2. **Checks whether macro assemblies are still used**: it uses Roslyn's `GetUsedAssemblyReferences` to check macro libraries and `HowMacro.Abstractions`,
   and confirms no other runtime dependency references them.
3. **Removes them from references and output**: MSBuild drops the macro assemblies not needed at runtime from the compile references and the copy-to-output list.
   As a result they disappear from the compiled assembly's metadata, from `deps.json` and from the output folder.

```
howmacro: expanded macros in 3 of 7 file(s), generated HowMacro.Startup.g.cs; not needed at runtime: HowMacro.Abstractions, Demo.Macros
```

Notes:

- **Conservative**: if the expanded code still uses an ordinary (non-macro) type from a macro library — say it calls `HowMacro.Macro.Quote` at runtime — that assembly is kept.
  If the analysis compilation has any error, nothing is removed.
- **The analysis must match the real compilation**: the project's `OutputType` and `Nullable` are passed to the engine, and sources are parsed with `DocumentationMode.Parse`;
  otherwise Roslyn can't tell what `cref`s in doc comments reference and counts every reference as used.
- **Can be turned off**: `-p:HowMacroRuntimeCleanup=false`. Off by default in the test helpers (it's slow); turn it on with `MacroTestOptions.RuntimeCleanup = true`,
  and read the result from `r.RuntimeUnused`.

## Debugging expansions: dump to a folder

You can write the expansion of **some source files**, or of **some macros**, to a folder and compare it side by side. This is only an extra copy for humans; it doesn't affect the expansion that is actually compiled.

```bash
# everything → howmacro-dump/ under the project
dotnet build samples/Demo.App -p:HowMacroDump=true

# only Player.cs, and only expand LOGGED and Save (other macros stay as they are)
dotnet build samples/Demo.App -p:HowMacroDumpFiles=Player.cs -p:HowMacroDumpMacros="LOGGED Save"

# a different folder
dotnet build samples/Demo.App -p:HowMacroDump=true -p:HowMacroDumpDir=/tmp/expanded
```

| Property | Meaning |
|---|---|
| `HowMacroDump=true` | Turns dumping on. Setting either filter property below turns it on too |
| `HowMacroDumpDir` | Target folder; defaults to `howmacro-dump` under the project (relative to the project directory) |
| `HowMacroDumpFiles` | Only write these files: relative paths or file names, `*` and `**` supported, separated by spaces |
| `HowMacroDumpMacros` | Only expand these macros (`LOGGED`, `Save`, with or without `@` and `[]`), separated by spaces |

The folder contains:

- **Expanded source files**: **line-aligned** with the originals — line N is source line N after expansion, so you can compare them side by side.
- **`generated/`**: the startup script the engine generated.
- **`_expansions.txt`**: the expansion report. It lists diagnostics and, for every expansion, the location, macro and source,
  plus the output **formatted over several lines** (the real expansion is folded onto one line and hard to read):

```
Player.cs:26  @LOGGED  (Member)
  source:
    [@Track, @Save] public int Gold = @LOGGED(100);
  output:
    public int Gold
    {
        get;
        set
        {
            if (global::System.Collections.Generic.EqualityComparer<int>.Default.Equals(field, value))
                return;
            ...
```

Notes:

- **Written even when expansion fails**, e.g. HMC013 (generated code doesn't compile) — exactly when you most need to see the expansion.
- **The dump folder is never compiled as source**: it's added to `DefaultItemExcludes`, so both command-line builds and the IDE exclude it;
  the expander also skips any folder containing a `.howmacro-dump` marker file.
- **Every dump clears the target folder**, but only folders howmacro created itself (with the marker file).
  It refuses to write into someone else's non-empty folder, to avoid deleting anything by mistake.
- Consider adding `howmacro-dump/` to `.gitignore`.
- When only some macros are expanded, unselected attribute macros don't run, so method macros that depend on their fragments get fewer fragments.

## Test helpers for macro authors

`HowMacro.Testing` lets macro authors expand a piece of source directly in a unit test. It isn't tied to a test framework; failed assertions throw `MacroTestException`,
which xUnit, NUnit and MSTest all treat as a test failure. Macros run inside the test process, with no need to build a project first. See `tests/Demo.Macros.Tests` for examples.

```csharp
var r = MacroTest.Expand(source, typeof(M).Assembly);

// 1. Test the expansion: expansion preserves line numbers, so source line 6 is r.Line(6)
r.AssertSuccess();
Assert.Equal("public class Player { public int Hp { get => Data.Hp; set => Data.Hp = value; } }", r.Line(6));

// 2. Test diagnostics: code, message, line
r.AssertError("HMC100", contains: "read-only", line: 6);

// 3. Test runtime behavior: compile and load the expansion (startup code runs immediately), then call the generated code
var compiled = r.Compile();
var player = compiled.Create("Demo.App.Player");
var log = MacroTest.CaptureConsole(() => compiled.Set(player, "Gold", 150));
Assert.Equal("[Player.Gold] 100 -> 150" + Environment.NewLine, log);
```

| API | Purpose |
|---|---|
| `MacroTest.Expand(source(s), references / options)` | Expand; `MacroTestOptions` can set `Macros` (expand only some macros), `Defines`, `Nullable`, etc. |
| `r.Output` / `r.Outputs` / `r.Line(n)` / `r.Startup` | Expanded text, a single line, the startup script |
| `r.Diagnostics` / `r.AssertSuccess()` / `r.AssertError(code, contains, line)` / `r.AssertWarning(...)` / `r.AssertNoWarnings()` | Diagnostic assertions |
| `r.Expansions` | A record of every expansion (macro, location, source, output, formatted output) |
| `r.DumpTo(dir, filePatterns)` | Write a dump folder just like a build does, handy when a test fails |
| `r.Compile()` → `Create` / `Get` / `Set` / `Call` / `IsProperty` | Compile and load the expansion, then drive the generated code through reflection |
| `MacroTest.CaptureConsole(action)` | Capture console output (for logging macros like LOG and LOGGED; requires disabling test parallelization) |

Run the sample tests:

```bash
dotnet test tests/Demo.Macros.Tests
```

## Key decisions

### 1. Intercept the compiler's input, never modify source files
`HowMacro.targets` runs before `CoreCompile`: it expands files containing macros into `obj/.../howmacro/src/`,
then swaps the original files in `@(Compile)` for the expanded copies and adds the startup script. Source files are never touched, so there's nothing to "restore", and a crash can't leave dirty files behind.
The IDE's design-time build skips this step, so the IDE always sees the original files.

See "Packaging and installation" for how to integrate. Consumers don't reference the expansion tool `HowMacro.Cli`, and it never appears in the program's output folder.

### 2. Macros are recognized semantically; `@` is a convention
The expander asks Roslyn "does the method this call actually binds to have `[Macro]`? Does this attribute class have `[AttributeMacro]`?" rather than searching for `@` in the text.
So `@"string"` and `@class` are never misread. Omitting the `@` gives warning HMC010, so readers can tell at a glance that it's a macro.

### 3. Three sites for method macros
| `MacroSite` | Replaced range | Example |
|---|---|---|
| `Expression` (default) | The call expression itself, parenthesized automatically | `var a = @SQUARE(x);` |
| `Statement` | The whole statement, wrapped in `{ }` | `@LOG(x);` |
| `Member` | The whole field declaration; the result must be a field or property with the same name and type | `public int Hp = @GETSET(...);` |

`Member` macros can read the declared `Name` / `Type` / `Modifiers` / `Attributes`,
so the field declaration itself becomes the syntax for passing arguments to the macro. `Attributes` contains only regular attributes; attribute macros are already stripped.

### 4. Attribute macro targets
`[AttributeMacro(MacroTarget.Field | MacroTarget.Property)]` declares which declarations it can mark (`Field` / `Property` / `Method` / `Type`).
Attribute macros can read `Target`, `Name`, `Type`, `Modifiers`, `ContainingType`, and the arguments written on the attribute (`Macro.ArgValue(0)`).

### 5. Macro output is syntax-checked first
Method macro output and attribute macro startup code are syntax-checked before use. Mistakes are reported as HMC011 at the macro's call site,
instead of as a baffling compiler error inside the expanded copy.

### 6. Line numbers: fold onto one line + pad newlines + `#line`
- Macro output is re-tokenized, stripped of comments and joined onto one line, landing on the line of the call.
- If the macro call itself spans N lines, N newlines are appended to the expansion, so the following line numbers don't change.
- The first line of each expanded file is `#line 1 "original path"`, so compile errors, `[CallerLineNumber]`, stack traces and breakpoints all point back to the original file.
- Every startup statement in the startup script is preceded by a `#line` pointing back to the attribute macro that produced it.

The `line check` and `stack frame` lines in the sample verify exactly this.

### 7. Macros must compile before the code that uses them
A macro has to be compiled and run before it can expand the project that uses it. There are two ways to satisfy this:

- The macro lives in a referenced macro library.
- The macro lives in a file inside the project marked with `HowMacroDefinition`. The expansion tool compiles these files separately first; see "Packaging and installation".

Otherwise, a macro compiled in the same compilation as its callers reports HMC004. In Unity this corresponds to a separate asmdef.

### 8. Macros never run at runtime
During expansion all arguments are passed as default values; macros read the source text with `Macro.Arg(i)` and constant values with `Macro.ArgValue(i)`.
If a macro does run at runtime (because the expansion step isn't enabled), `Macro.*` throws a clear exception instead of silently returning a wrong result.

## Known issues and next steps

1. **Remaining "field vs property" differences**: uses detectable at compile time are already checked by HMC017. Two cases remain:
   - Reflection or serialization that looks members up as fields at runtime (e.g. a field-only serializer) won't find the member.
   - Whole-text replacement in region macros isn't covered by HMC017 yet; per-member replacement is.
2. **The expansion compilation doesn't run source generators**: when callers depend on types produced by source generators, argument types may not be inferable,
   and the HMC013 check may report false positives. This needs a `GeneratorDriver` pass over `@(Analyzer)` first.
3. **Scope of semantic information**: currently covers type and member declarations only, not control-flow or data-flow analysis inside method bodies.
   Member lists include only members declared explicitly in source, not inherited ones (walk up via `BaseType` yourself).
4. **Debugging**: expanded code sits on one line, so you can't step into the inside of an expansion. Some debuggers may warn that the source checksum doesn't match (the PDB records the checksum of the expanded copy).
5. **Performance**: every build runs a full semantic analysis, plus a compile check of macro-generated code and runtime cleanup (two more full analyses).
   Caching by "source files + macro assembly hash" could come later.
6. **Unity**: integrate by intercepting the compiler's input, reusing `HowMacro.Engine`; switch the startup script's entry attribute to Unity's.
